2坑一：建库与查询的嵌入模型不一致，检索"静默失败"

现象：向量库建好了，数据也有，但无论问什么，相似度检索都返回空或明显无关的结果，且不报任何错误。

排查：分别打点建库和查询时实际使用的嵌入模型，发现维数对不上。

# 建库脚本 build_vector_db.py
model = "mxbai-embed-large-v1"      # 1024 维

# 查询端 tools.py
model = "all-MiniLM-L6-v2"          # 384 维
维度不一致意味着：存进去的向量和查询向量无法在同一个空间比较相似度，检索自然全部失效——而且因为是"可运行但结果空白"，属于最难定位的静默故障。

根因

Chroma 在 upsert 时用建库模型定下集合的向量维数，查询时若向量维数对不上，轻则空结果、重则直接 InvalidDimensionException。

解决

把嵌入模型收敛为单一配置源，并加回归测试守卫防止再次漂移：

3坑二：多知识源的检索结果"拼接不等于融合"

项目有商品目录（catalog_chunks）和政策文档（policies）两个向量集合。早期实现是"每个源各取 top-k，然后按源顺序拼接"。

问题：商品集有 9288 条、政策集只有 8 条。拼接后商品结果永远排前面，弱源（政策）的高相关召回被淹没；同一条内容跨源重复召回，上下文里噪音多、排序不稳定。

解决：实现 RRF（Reciprocal Rank Fusion）倒数排名融合：

# RRF 核心：按"倒数排名"聚合多个源的排序信号
score(doc) = Σ_sources  1 / (rank_in_source + K)   # K=60

# 一条文档在多个源里都排得靠前 → 融合分高，天然去重
def fuse(groups):
    scores = {}
    docs = {}
    for group in groups:             # 每个源自己的 top-k
        for rank, doc in enumerate(group):
            key = doc["text"].lower()
            scores[key] = scores.get(key, 0) + 1.0 / (60 + rank + 1)
            docs.setdefault(key, doc)
    return [docs[k] for k, _ in sorted(scores.items(),
                                       key=lambda kv: kv[1], reverse=True)]
对比效果：同样一批查询，RRF 返回更少的重复噪音、跨源高相关文档排在更前； 用合成多源数据做单测，共享文档被正确去重并升至首位。融合算法本身可脱离服务单独可测。

延伸：chroma 0.5.x 的落盘坑

进一步发现，多线程并发 upsert 会让 chroma 0.5.x 丢失 HNSW 向量段（sqlite/pickle 在，但查询报 Cannot open header file）。规避方法很直接：

  • 嵌入层并发（网络 IO 密集，用 ThreadPool）
  • 写入层串行批量 add（避免并发触发 chroma 的段写缺陷）
# 可行的灌库模式：线程嵌入 + 顺序批量写入
with ThreadPoolExecutor(8) as ex:
    vecs = list(ex.map(embed_text, chunk_docs))   # 并发取 embedding
col.add(ids=ids, embeddings=vecs, documents=chunk_docs)  # 顺序 add

4坑三：Agent 编排框架的 API 迁移

项目2 的 agent 示例基于已停产的 adk 包，官方新版本是 google-adk，API 变了。

# 旧（停产）        vs        # 新（官方）
from adk.tools import Tool      from google.adk.agents import Agent, SequentialAgent
                                from google.adk.tools import FunctionTool

迁移时踩到一个细节：SequentialAgent 只接受 sub_agents，tools 参数属于 Agent / LlmAgent，照文档写会直接报参数不支持。

教训：升级第三方框架大版本时，先查官方迁移文档，不要照搬旧写法；用最小用例验证 API 签名。

5总体复盘

类别踩的坑解法
RAG嵌入模型不一致致静默失败单一配置源 + 一致性测试
RAG多源拼接排序不稳、重复RRF 融合重排 + 去重
存储chroma 0.5.x 并发写丢段线程嵌入 + 顺序 add
编排adk 旧 API 停产迁移 google-adk 新 API
部署远程模型依赖外网Ollama 本地嵌入/生成

这些坑的共同点：都是"能跑但结果不对 / 换环境就挂"的隐性工程问题，单靠功能测试覆盖不到，需要专门的检索评估与回归测试来兜底。这也是二开这类项目最有价值的部分——不是把功能做出来，而是把"可靠性"夯实。
